Why This Talk Matters

The reproducibility crisis is a shared responsibility

The Reproducibility Crisis

The Problem

A significant fraction of published biomedical results cannot be reproduced. This is not just a statistics problem — it is a data practices problem.
Major culprits:
Poor or missing documentation
Unmaintained code
Lost or overwritten files
Undescribed methods and parameters
"An article about computational science in a scientific publication is not the scholarship itself, it is merely advertising of the scholarship."
— Buckheit & Donoho, 1995

Data Is Only As Good As the Practices Behind It

Protect

Raw data is your most valuable asset. Treat it as read-only. Always.

Document

Every manual step that is not recorded is a potential source of irreproducibility.

Repeat

The question is not "does this work?" but "can future me repeat this?"
Good data practices are not about perfectionism — they are about self-preservation

A Peek Into Bioinformatics Work

Data types, assays, pipelines, and how to read the results

What Is Bioinformatics Data?

What it is

Biological information stored, processed, and interpreted computationally — DNA, RNA sequences, counts, intensities, coordinates, and clinical variables.

The scale

A single -omics experiment can generate billions of reads. Scale is not just a technical challenge — it shapes every analytical decision.
Counts — RNA-seq read counts per gene; scRNA-seq UMI counts per cell per gene
Sequences — DNA/RNA base pairs stored as FASTQ; genome assemblies in FASTA; variant calls in VCF
Peaks — Chromatin accessibility (ATAC-seq), histone marks (ChIP-seq), transcription factor binding sites
Raw Spectra — Mass-to-charge ratio profiles representing peptide or metabolite identity and abundance in proteomics and metabolomics
Clinical — Age, treatment, diagnosis, survival outcomes

Common File Formats: Sequences & Alignments

FASTA .fa / .fasta

Reference sequences: genomes, transcripts, proteins. A > header line, then the sequence. 
>chr17 Homo sapiens chromosome 17, GRCh38
GATGGGATTGGGGTTTTCCCCTCCCATGTGCTCAAGACTGGCGCTAAAAG
TTTTGAGCTTCTCAAAAGTCTAGAGCCACCGTCCAGGGAGCAGGTAGCTG

FASTQ .fastq.gz

Raw sequencing reads straight off the sequencer. Four lines per read: ID, sequence, +, per-base quality scores. 
@SRR001666.1 read1/1                        # read ID
GATTTGGGGTTCAAAGCAGTATCGATCAAATAGTAAATCC    # sequence
+                                           # separator
!''*((((***+))%%%++)(%%%%).1***-+*''))**    # Phred quality, one per base

SAM / BAM .bam

Reads aligned to a reference genome. BAM is the compressed binary form; view it with samtools view. Needs a .bai index. 
# QNAME FLAG CHR   POS     MAPQ CIGAR MATE POS     TLEN SEQ      QUAL
read1   99   chr17 7674220 60   40M   =    7674380 200  GATTTG.. IIIIII..

Common File Formats: Variants & Genomic Regions

VCF .vcf.gz

Variant calls: SNVs, indels. ## lines hold metadata (including the genome build), then one row per variant with a genotype per sample. 
##fileformat=VCFv4.2
##reference=GRCh38
#CHROM POS     ID REF ALT QUAL FILTER INFO          FORMAT SAMPLE1
chr17  7675088 .  C   T   812  PASS   DP=64;AF=0.48 GT:DP  0/1:64

BED .bed

Genomic regions: genes, peaks, target panels. Tab-separated: chromosome, start, end, then optional name, score, strand. 
# chrom  start     end       name   score  strand
chr17    7668401   7687550   TP53   0      -
chr7     55019016  55211628  EGFR   0      +
chr1     1000000   1000500   peak_1 850    .
Coordinates differ: BED is 0-based, while VCF and SAM/BAM are 1-based. Mixing them silently shifts every position by one.
Always check the genome build: hg19 and hg38 coordinates for the same gene are different. Files from different builds cannot be combined directly.

What to Be Aware of in a Bioinformatics Project

Batch Effects — Samples processed on different days, machines, or by different people introduce technical variation that can mask or mimic biology
Sample Size — Underpowered studies are one of the most common and unrecoverable problems in bioinformatics
Metadata Quality — Missing or inconsistent sample metadata can make an entire dataset unanalyzable
Reference Genomes — Which genome build? hg38 vs hg19 matters. Never assume.
Multiple Testing — Thousands of genes tested simultaneously — correction is not optional
Key message: These are not analysis problems — they are design and communication problems

Asking the Right Questions to Your Collaborator

Before the Experiment

What is the biological question?
What effect size do you expect?

About the Samples

How were samples collected, stored, and processed?
Are there any known confounders or batch effects?

About the Data

Which assay to use?
What is the expected sequencing depth?
What file formats will be delivered?

About the Analysis

What tools are being used and why?
What parameters were chosen?

About the Output

What does a positive result look like?
How will results be validated experimentally?
A good question asked before the experiment saves weeks of analysis after it

Questions to Ask When You Receive Results

1
QC: Were any samples or features removed? Why?
2
Statistics: What multiple testing correction was applied? Are effect sizes shown alongside p-values?
3
Parameters: What thresholds were used? Are results sensitive to those choices?
4
Reproducibility: Can this be re-run exactly? Is there a script?
5
Biology: Do the results make biological sense? What is the next experiment?
Receiving results is not the end of the conversation — it is the middle of it
If your analyst cannot answer questions 1–4, that is a reproducibility warning sign

The Two Rules That Change Everything

From Noble (2009) — PLoS Computational Biology

Noble (2009) — The Paper Behind These Principles

PLoS Computational Biology | 2009 | Open Access
"A Quick Guide to Organizing Computational Biology Projects"
William Stafford Noble — University of Washington
Rule 1: "Someone unfamiliar with your project should be able to look at your computer files and understand in detail what you did and why."
Rule 2: "Everything you do, you will probably have to do over again."

Why it matters

These two rules are not about aesthetics or perfectionism. They are practical requirements for science that can be trusted, published, and built upon.

Free to read

doi:10.1371/journal.pcbi.1000424
Recommended reading for every new trainee before they write a single line of code.

Rule 1: Write for a Stranger — Who Is Probably You

"Someone unfamiliar with your project should be able to look at your computer files and understand in detail what you did and why."
— Noble, 2009

The stranger

Is most often you, six months from now

The problem

You will not remember what you did, or why you did it

The solution

Good organization is not perfectionism — it is self-preservation

Rule 2: You Will Have to Do It Again

"Everything you do, you will probably have to do over again."
— Noble, 2009
If disorganized:
Starting over is painful — nothing is findable, nothing is repeatable
If organized:
Repeating is straightforward — re-run the script, update the date, done

When does "again" happen?

New data arrives
A parameter was wrong
A reviewer asks for a different analysis
A collaborator joins the project
A new trainee takes over

Why Date Your Directories?

Logical names fail over time:
analysis_with_batch_correction/

Six months later: Which batch correction? Which samples? Which genome build?
Date-stamped directories tell the story automatically
results/
├── 2024-01-10/  ← pilot analysis
├── 2024-03-15/  ← added new samples
├── 2024-05-02/  ← reviewer response
└── 2025-01-20/  ← updated reference genome
Optionally, add a word or two to indicate the topic — but the date always comes first

The Lab Notebook & Driver Scripts

Documentation habits that make your work reproducible

Your Lab Notebook Lives in Your Results Folder

What to record

Exactly what you did
What you observed
Your conclusions
Ideas for future experiments
Notes from meetings and emails
"Particularly when an experiment turns out badly, document how you know it failed — the interpretation may not be obvious to someone else." — Noble, 2009

Format

Tools that work well

Quarto document, R Markdown, plain Markdown file, or even a well-structured text file

The runall Script: Your Experiment in One File

What it is

A single driver script that re-runs your entire experiment automatically — from raw data to final figures

Noble's 5 rules

1
Record every operation
2
Comment generously
3
Never edit intermediate files by hand
4
Use relative pathnames
5
Make the script restartable
# runall.sh
# Date: 2024-03-15
# Purpose: Full DE analysis
# Author: Kalyanee Shirlekar

# Step 1: QC raw reads
if [ ! -f results/qc_done.txt ]; then
  bash src/run_qc.sh
  touch results/qc_done.txt
fi

# Step 2: Align to hg38
if [ ! -f results/aligned.bam ]; then
  bash src/align.sh
fi

# Step 3: Differential expression
Rscript src/de_analysis.R

# Step 4: Summarize results
Rscript src/summarize.R

Version Control: Your Time Machine

Backup, history, and collaboration

Three Reasons Version Control Matters

1. Backup

A reliable, offsite snapshot of your work at every stage — never lose a working version again

2. Historical Record

Re-run an experiment exactly as it was three months ago — just check out that version

3. Collaboration

Multiple people, same files, no chaos — changes are tracked and merged automatically
Git is to your code what Track Changes is to your Word document — but far more powerful

Training Resources

UFRC offers free Git, Python, and Bash training workshops. Sign up at docs.rc.ufl.edu/training and subscribe to their mailing list to receive announcements.

What NOT to Put Under Version Control

Do NOT commit:
Large raw data files (FASTQ, BAM)
Automatically generated results
Compiled binaries
Sensitive or identifiable patient data
DO commit:
Scripts and code
Configuration files
README and documentation
Small metadata files

The simple rule

If a script generates it, do not track it.
If you type it, track it.

The README File: A Gift to Your Future Self

What is a README?

A plain text or Markdown file placed at the root of every project folder. It is the first thing anyone — including future you — should read to understand what the project is and how to use it.

How to create one

touch README.md — then open and fill it in. One file, always in the same place, always up to date.

What to document

Project title and purpose
Author name and date started
Folder structure overview
How to run the analysis (e.g., bash runall.sh)
Software versions and dependencies
Input data sources and descriptions
Any known issues or caveats
Think of the README as a gift to your future self — and to every collaborator who comes after you

Reproducibility in Practice

Raw Data: Untouchable

Keep raw data read-only. All processing happens in scripts. Never modify the original file.

Scripts Over Clicks

Prefer scripted workflows over point-and-click tools for any analysis you will ever need to repeat.

Share Your Environment

Share code, package versions, and runtime environments when publishing or handing off work.

Environment Management Tools

Conda / Mamba — Create isolated software environments; share via environment.yml

renv (R) — Lock R package versions per project; collaborators restore with renv::restore()

Docker / Singularity — Container images that capture the entire computing environment; Singularity is supported on HiPerGator
A reproducible analysis: someone else runs your script on your data and gets the same result — every time
